Bitburner Script Suite Manual - Version 2.2
==========================================

Status
------
This document describes the Version 2.2 Bitburner automation suite.

Version 2.2 keeps the Version 2 architecture, but adds a spare-capacity rental/share layer and improves the operational dashboard with compact v3 health reporting, timing forecasts, purchased/cloud server reporting, and share-cycle visibility.

The suite is designed around these responsibilities:

- deployment and refresh from home;
- persistent per-target process management;
- low-RAM target support via remote worker hosts;
- purchased/cloud server buying and upgrading;
- spare RAM conversion into faction reputation via ns.share();
- operational reporting and forecasting;
- server-level log inspection;
- controlled cleanup/reset;
- optional file discovery and worm-style propagation support.

The main operational dashboard is still check-infection.js.

Core Concepts
-------------

1. Deployment layer

   upload.js copies the current script bundle from home to reachable rooted servers.

2. Management layer

   process.js watches one money target and decides whether it currently needs weaken, grow, or hack.

3. Worker layer

   weaken.js, grow.js, and hack.js are tiny one-shot scripts launched by process.js.

4. Remote assignment layer

   assign-targets.js runs process.js on larger worker hosts for money servers that cannot sensibly manage themselves.

5. Purchased/cloud server layer

   buy-servers.js spends a fraction of home cash to buy missing purchased/cloud servers, then upgrades existing ones once the limit is full.

6. Spare-capacity rental/share layer

   rent-capacity.js scans available rooted hosts and launches rent-share.js into unused RAM.

   rent-share.js loops ns.share(). In practical Bitburner terms this converts spare RAM into faction reputation support. It does not generate direct cash.

7. Operational dashboard

   check-infection.js reports root/deployment/process status, RAM usage, purchased/cloud server status, restart recommendations, active weaken/grow/hack/share cycles, and approximate next-cycle forecasts.

8. Diagnostics

   logview.js shows script logs for one selected server.

9. Cleanup/reset

   clean.js kills selected framework scripts across the network.

10. Discovery and optional propagation

   iteration.js catalogues files discovered on remote hosts. The infect*.js scripts remain as optional worm-style propagation helpers, but central deployment through upload.js is the normal path.

Normal Operating Model
----------------------

Recommended normal command:

    run startup.js true false

This normally:

1. cleans managed framework scripts;
2. runs upload.js;
3. runs assign-targets.js;
4. starts rent-capacity.js;
5. starts check-infection.js.

Recommended expansion command:

    run buy-servers.js 0.4

Then redeploy:

    run startup.js true false

Or buy and redeploy in one startup run:

    run startup.js true true 0.4

Script Reference
================

startup.js
----------

Purpose
~~~~~~~
startup.js is the one-command orchestrator for restart, augmentation, or manual recovery.

Expected location
~~~~~~~~~~~~~~~~~
home only.

Typical commands
~~~~~~~~~~~~~~~~

Clean/deploy/assign/start rental/dashboard:

    run startup.js true false

Clean, buy/upgrade using 40% of current home cash, then deploy:

    run startup.js true true 0.4

Full argument pattern
~~~~~~~~~~~~~~~~~~~~~

    run startup.js [clean] [buyServers] [buySpendRatio] [assignMinRam] [assignPerHost] [assignAllowMoneyHosts] [startRent] [rentReserveGb] [rentTargetUsePct] [rentLoopMs] [rentMinThreads] [rentIncludeHome]

Parameters
~~~~~~~~~~

1. clean
   Boolean. Default true. Runs clean.js managed before deployment.

2. buyServers
   Boolean. Default false. Runs buy-servers.js before deployment.

3. buySpendRatio
   Number. Default 0.5. Fraction of home cash to spend when buying/upgrading.

4. assignMinRam
   Number. Default 1. Minimum RAM for remote worker hosts.

5. assignPerHost
   Number. Default 2. Maximum remote targets per worker host.

6. assignAllowMoneyHosts
   Boolean. Default true. Allows money servers to act as worker hosts.

7. startRent
   Boolean. Default true. Starts rent-capacity.js after assignment.

8. rentReserveGb
   Number. Default 8. RAM to leave free on each rental host.

9. rentTargetUsePct
   Number. Default 0.98. Target maximum RAM usage fraction for rental filling.

10. rentLoopMs
    Number. Default 5000. rent-capacity.js loop delay.

11. rentMinThreads
    Number. Default 1. Minimum rent-share.js threads to launch on a host.

12. rentIncludeHome
    Boolean. Default false. Whether home may be used for rent-share.js.

Pseudocode
~~~~~~~~~~

    assert host is home
    parse startup, assignment, purchase, and rental args
    verify required scripts exist
    if clean requested:
        run clean.js managed and wait
    if buy requested:
        run buy-servers.js spend ratio and wait
    run upload.js and wait
    run assign-targets.js with assignment settings and wait
    if startRent:
        start rent-capacity.js with rental settings
    remove stale restart-required.txt after successful orchestration
    start check-infection.js

Operational notes
~~~~~~~~~~~~~~~~~
startup.js is the preferred entry point after augmentation/restart.


upload.js
---------

Purpose
~~~~~~~
upload.js is the central deployment and refresh script. It scans the reachable network, attempts root where possible, copies the framework payload, and starts the first runtime layer.

Expected location
~~~~~~~~~~~~~~~~~
home only.

Typical command
~~~~~~~~~~~~~~~

    run upload.js

Optional worm mode, if used:

    run upload.js true

Pseudocode
~~~~~~~~~~

    assert host is home
    define payload scripts
    verify required home files exist
    scan all servers from home
    for each rooted/reachable server:
        copy current framework scripts
        start process.js locally when suitable
        start iteration.js where possible
        optionally start infect.js propagation
    print deployment summary

Operational notes
~~~~~~~~~~~~~~~~~
upload.js is safe to run directly, but startup.js normally runs it for you.


assign-targets.js
-----------------

Purpose
~~~~~~~
assign-targets.js assigns unmanaged or low-RAM money targets to larger remote worker hosts.

Expected location
~~~~~~~~~~~~~~~~~
home only.

Typical commands
~~~~~~~~~~~~~~~~

Normal:

    run assign-targets.js 1 2

Conservative:

    run assign-targets.js 1 1

Avoid money servers as worker hosts:

    run assign-targets.js 1 2 false

Parameters
~~~~~~~~~~

1. minWorkerRam
   Default 1. Minimum RAM for a host to be considered.

2. maxAssignmentsPerHost
   Default 2. Maximum remote process.js managers per worker host.

3. allowMoneyHosts
   Default true. Whether money servers can also host remote managers.

Pseudocode
~~~~~~~~~~

    assert host is home
    kill existing remote process/worker assignments
    identify rooted money targets needing remote management
    identify candidate worker hosts
    copy process/worker scripts to worker hosts
    assign high-value targets first
    start process.js on worker host with target as argument
    print assignment summary


process.js
----------

Purpose
~~~~~~~
process.js is the persistent controller for one target. It may run locally on the target or remotely on a larger host.

Expected location
~~~~~~~~~~~~~~~~~
Any rooted non-home server with enough RAM.

Parameters
~~~~~~~~~~

    run process.js [target] [securityBuffer] [moneyTargetRatio] [hackTargetRatio] [sleepMs]

Defaults:

- target: current host;
- securityBuffer: 5;
- moneyTargetRatio: 0.85;
- hackTargetRatio: 0.10;
- sleepMs: 5000.

Pseudocode
~~~~~~~~~~

    host = current hostname
    target = arg0 or host
    reject home host
    verify target/root/RAM
    loop:
        if target has no money:
            write idle process-state.json
        else if security is above minimum + buffer:
            launch weaken.js
        else if current money is below target ratio:
            launch grow.js
        else:
            launch hack.js
        kill obsolete worker type for this target
        write process-state.json
        sleep

Operational notes
~~~~~~~~~~~~~~~~~
Do not normally run process.js directly. Let upload.js and assign-targets.js manage it.


weaken.js / grow.js / hack.js
-----------------------------

Purpose
~~~~~~~
These are one-shot worker scripts. Each performs a single Bitburner operation against a target and exits.

Typical parent
~~~~~~~~~~~~~~
process.js

Typical direct test commands
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    run weaken.js 10 targetServer
    run grow.js 10 targetServer
    run hack.js 10 targetServer

Operational notes
~~~~~~~~~~~~~~~~~
Keep these scripts tiny. process.js owns the decision loop.


buy-servers.js
--------------

Purpose
~~~~~~~
buy-servers.js buys and upgrades purchased/cloud servers using a percentage of current home cash.

Expected location
~~~~~~~~~~~~~~~~~
home only.

Typical commands
~~~~~~~~~~~~~~~~

Spend 40%:

    run buy-servers.js 0.4

Dry run, if wanted:

    run buy-servers.js 0.4 pserv- true

Full argument pattern
~~~~~~~~~~~~~~~~~~~~~

    run buy-servers.js [spendRatio] [prefix] [dryRun] [tail]

Parameters
~~~~~~~~~~

1. spendRatio
   Default 0.5. Fraction of current home cash to spend.

2. prefix
   Default pserv-. Purchased/cloud server name prefix.

3. dryRun
   Default false. Reports actions without performing them.

4. tail
   Default true. Opens a tail window.

Current v2.2 behaviour
~~~~~~~~~~~~~~~~~~~~~~

- Uses Bitburner cloud/purchased server APIs where available.
- Deletes stale restart-required.txt at the start.
- Fills missing server slots first.
- Once the limit is full, upgrades the smallest useful servers first.
- Writes restart-required.txt only if capacity actually changed.
- Supports dry-run reporting.

Operational notes
~~~~~~~~~~~~~~~~~
If capacity changed, run:

    run startup.js true false


rent-capacity.js
----------------

Purpose
~~~~~~~
rent-capacity.js fills spare network RAM with rent-share.js workers.

In current Bitburner terms, this is not literal cash rental. It is a spare-capacity share layer using ns.share(), useful for faction reputation gain while leaving RAM available for the core hacking framework.

Expected location
~~~~~~~~~~~~~~~~~
home only.

Typical commands
~~~~~~~~~~~~~~~~

Default:

    run rent-capacity.js

Explicit defaults:

    run rent-capacity.js 8 0.98 5000 1 false rep

Argument pattern
~~~~~~~~~~~~~~~~

    run rent-capacity.js [reserveGb] [targetUsePct] [loopMs] [minThreads] [includeHome] [mode]

Parameters
~~~~~~~~~~

1. reserveGb
   Default 8. RAM kept free on each host.

2. targetUsePct
   Default 0.98. Maximum target host RAM utilisation.

3. loopMs
   Default 5000. Scan/relaunch delay.

4. minThreads
   Default 1. Minimum threads needed before launching rent-share.js.

5. includeHome
   Default false. Whether home may be used as a share host.

6. mode
   Default rep. Currently maps to ns.share() reputation sharing.

Pseudocode
~~~~~~~~~~

    assert host is home
    verify rent-share.js exists
    loop:
        scan all rooted hosts
        exclude home unless includeHome is true
        copy rent-share.js where missing
        compute free RAM after reserve and target use cap
        launch rent-share.js where enough threads fit
        print compact utilisation/share summary
        sleep

Operational notes
~~~~~~~~~~~~~~~~~
This should run after upload.js and assign-targets.js, so core work gets RAM first and only spare space is shared.


rent-share.js
-------------

Purpose
~~~~~~~
Tiny worker script for rent-capacity.js.

Pseudocode
~~~~~~~~~~

    loop forever:
        await ns.share()

Operational notes
~~~~~~~~~~~~~~~~~
Do not run manually unless testing. rent-capacity.js handles placement and thread counts.


check-infection.js
------------------

Purpose
~~~~~~~
check-infection.js is the primary compact v3 operational dashboard.

It reports:

- rooted/deployed/staged server counts;
- money server management state;
- local versus remote process.js coverage;
- active weaken/grow/hack/share cycles;
- current and maximum money;
- RAM use across network and purchased/cloud servers;
- purchased/cloud server capacity and activity;
- buy-servers.js/restart-required.txt status;
- rent-capacity.js/rent-share.js status;
- approximate forecast rows for next weaken/grow/hack timings and likely value;
- drill-down issues and recommended next commands;
- AI handoff JSON for quick copy/paste diagnosis.

Expected location
~~~~~~~~~~~~~~~~~
home.

Typical command
~~~~~~~~~~~~~~~

    run check-infection.js

Full argument pattern
~~~~~~~~~~~~~~~~~~~~~

    run check-infection.js [maxTableRows] [showNonMoneyRows] [colour] [securityBuffer] [moneyTargetRatio] [hackTargetRatio] [forecastRows]

Defaults:

- maxTableRows: 120;
- showNonMoneyRows: false;
- colour: true;
- securityBuffer: 5;
- moneyTargetRatio: 0.85;
- hackTargetRatio: 0.10;
- forecastRows: 18.

Common examples
~~~~~~~~~~~~~~~

Show more rows:

    run check-infection.js 200

Include non-money servers:

    run check-infection.js 200 true

Disable colour:

    run check-infection.js 120 false false

Operational notes
~~~~~~~~~~~~~~~~~
This is the script to trust for board-level status. Use logview.js only when the dashboard identifies a specific server worth inspecting.

Interpreting check-infection.js
===============================

Common statuses
---------------

good
    Healthy.

partial
    Working, but incomplete.

poor
    Needs attention.

busy
    RAM is active. Usually good.

idle
    RAM or hosts are available but unused.

restart
    Capacity changed. Redeploy recommended.

watch
    Not necessarily broken, but worth observing.

Common reasons
--------------

managed
    Locally managed by process.js.

remoteManaged
    Managed by process.js running on another host.

lowRam
    Cannot locally run process.js. Use assign-targets.js.

noProcess
    process.js exists but no local/remote manager is seen.

missingProcessFile
    Deployment incomplete.

processIdle
    process.js is running but no worker was visible at scan time. Often a timing artefact.

nonMoney
    Server has no money and does not need a money cycle.

noRoot
    Root missing.

share
    Spare-capacity rent-share.js work is running.

Version 2.2 Design Notes
========================

Why the share layer exists
--------------------------
n
The hacking framework should get first claim on RAM. But completely idle RAM is wasted. rent-capacity.js opportunistically fills spare RAM with ns.share() workers, while leaving a reserve and respecting a target utilisation cap.

Why startup.js starts rent-capacity.js after assignment
-------------------------------------------------------

Remote process managers and workers are more important than reputation sharing. Starting rent-capacity.js last makes it behave as a filler layer rather than competing with the core hack/grow/weaken system.

Why check-infection.js includes forecasts
-----------------------------------------

process.js is adaptive rather than a fixed batch scheduler. Forecasts therefore estimate what is likely to happen next: whether the target needs weaken, grow, or hack, roughly how long the operation takes, and the expected value if a hack phase is likely.

Why restart-required.txt still exists
-------------------------------------

buy-servers.js can change available capacity. After that, upload.js and assign-targets.js should run again so new or upgraded hosts receive scripts and can be used.
