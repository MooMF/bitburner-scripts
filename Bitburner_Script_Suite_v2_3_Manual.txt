Bitburner Script Suite Manual - Version 2.3
================================================

Purpose
-------
This document describes the Bitburner v2.3 automation suite currently built around:

- one-command startup and recovery;
- central deployment from home;
- remote target assignment for low-RAM targets;
- persistent per-target weaken/grow/hack controllers;
- controlled spare-RAM share/rental use;
- manager-console diagnostics backed by focused JSON report scripts;
- optional file discovery, contract triage, and experimental faction support.

The normal operator entry points are:

    run startup.js true false
    run check-infection.js
    run manager-console.js

`check-infection.js` is now a compatibility wrapper. It delegates to `manager-console.js`.


===============================================================================
SECTION 1 - SCRIPT USAGE
===============================================================================

1.1 Normal startup
------------------

Recommended default launch:

    run startup.js true false

Meaning:

    clean existing managed scripts: yes
    buy/upgrade servers: no
    deploy scripts: yes
    assign remote targets: yes
    start rent/share manager: yes
    launch check-infection.js wrapper: yes

Full argument form:

    run startup.js [clean] [buyServers] [buySpendRatio] [assignMinRam] [assignPerHost] [assignAllowMoneyHosts] [startRent] [rentMaxSharePct] [rentReserveGb] [rentIncludeHome] [rentLoopMs]

Arguments:

    clean                 Boolean. Default true.
                          If true, startup runs clean.js managed and clean.js share.

    buyServers            Boolean. Default false.
                          If true, startup runs buy-servers.js before deployment.

    buySpendRatio         Number. Default 0.5.
                          Fraction of home cash to spend if buyServers is true.

    assignMinRam          Number. Default 1.
                          Minimum RAM for a host to be considered by assign-targets.js.

    assignPerHost         Number. Default 2.
                          Maximum remote target managers per worker host.

    assignAllowMoneyHosts Boolean. Default true.
                          Whether money-bearing servers can be used as remote worker hosts.

    startRent             Boolean. Default true.
                          Whether startup should restart rent-capacity.js.

    rentMaxSharePct       Number. Default 60.
                          Maximum percentage of each eligible host that rent-capacity.js may devote to share.

    rentReserveGb         Number. Default 1024.
                          Additional RAM reserve per share-capable host.

    rentIncludeHome       Boolean. Default false.
                          Whether home is eligible for rent/share workers.

    rentLoopMs            Number. Default 10000.
                          rent-capacity.js loop delay.

Examples:

    run startup.js true false

        Normal clean startup. Does not buy servers.

    run startup.js true true 0.4

        Clean startup, first spending 40% of home cash on purchased/cloud servers.

    run startup.js true false 0.5 1 2 true true 60 1024 false 10000

        Explicit normal startup with rent/share cap at 60%, 1TB reserve per host,
        home excluded, and a 10 second rent manager loop.

    run startup.js false false

        Redeploy without the clean phase. Useful only when you deliberately want
        currently running managed scripts left alone.


1.2 Main console and dashboard
------------------------------

Compatibility dashboard command:

    run check-infection.js

Equivalent direct command:

    run manager-console.js

Detailed views:

    run manager-console.js overview
    run manager-console.js runtime
    run manager-console.js money
    run manager-console.js security
    run manager-console.js payouts
    run manager-console.js share
    run manager-console.js actions
    run manager-console.js server 4sigma

Notes:

- `overview` gives a high-level operational summary.
- `runtime` focuses on root, deployment, manager processes, and worker cycles.
- `money` shows money fill state by target.
- `security` shows security excess and weaken ETA by target.
- `payouts` shows whether targets are hack-ready and what the next hack value may be.
- `share` shows the spare-RAM share/rental layer.
- `actions` prints command suggestions from current reports.
- `server <name>` gives a focused cross-report view for one server.


1.3 Deployment
--------------

Deploy scripts from home:

    run upload.js

Optional worm/staged infection mode:

    run upload.js true

Normal use is through startup.js. Direct use is useful when you have edited scripts and want to refresh remote copies without changing purchased servers or target assignments.

`upload.js` deploys the core runtime payload and removes stale remote `rent-capacity.js` copies. `rent-capacity.js` is home-level; `rent-share.js` is the remote worker script.


1.4 Remote assignment
---------------------

Assign low-RAM or unmanaged money targets to larger worker hosts:

    run assign-targets.js 1 2

Arguments:

    run assign-targets.js [minWorkerRam] [maxAssignmentsPerHost] [allowMoneyHosts]

Examples:

    run assign-targets.js 1 2
        Normal assignment.

    run assign-targets.js 1 1
        Conservative assignment; fewer remote managers per host.

    run assign-targets.js 1 3
        More aggressive assignment; more target managers per host.

    run assign-targets.js 1 2 false
        Avoid using money-bearing servers as worker hosts.

Normal use is through startup.js.


1.5 Purchased/cloud server expansion
------------------------------------

Buy or upgrade purchased/cloud servers:

    run buy-servers.js 0.4

Arguments:

    run buy-servers.js [spendRatio] [prefix] [dryRun] [tail]

Defaults:

    spendRatio  0.5
    prefix      pserv-
    dryRun      false
    tail        true

Examples:

    run buy-servers.js 0.4
        Spend 40% of home cash.

    run buy-servers.js 0.5 pserv- true
        Dry-run a 50% spend plan using the pserv- naming convention.

    run startup.js true true 0.4
        Clean, buy/upgrade using 40% of cash, deploy, assign, and restart share.

If buy-servers.js changes capacity, it writes `restart-required.txt`. A successful startup clears that marker after redeployment.


1.6 Money target controller
---------------------------

Persistent target controller:

    run process.js target

Argument form:

    run process.js [targetServer] [securityBuffer] [moneyTargetRatio] [hackTargetRatio] [sleepMs]

Defaults:

    targetServer      current host
    securityBuffer    5
    moneyTargetRatio  0.85
    hackTargetRatio   0.10
    sleepMs           5000

Examples:

    run process.js joesguns
    run process.js 4sigma 5 0.90 0.05 5000

Normal use is not direct. `upload.js` starts local process managers where possible. `assign-targets.js` starts remote process managers for targets that should be managed from larger hosts.


1.7 Worker scripts
------------------

One-shot workers:

    run weaken.js target
    run grow.js target
    run hack.js target

These are normally launched by process.js. They should stay small and single-purpose.

Direct use is diagnostic only.


1.8 Share/rental capacity
-------------------------

Controlled spare-RAM sharing:

    run rent-capacity.js

Argument form:

    run rent-capacity.js [maxSharePct] [reserveGb] [includeHome] [loopMs]

Defaults:

    maxSharePct  60
    reserveGb    1024
    includeHome  false
    loopMs       10000

Examples:

    run rent-capacity.js 60 1024 false 10000
        Default style: allow up to 60% share use on eligible hosts, reserve 1TB.

    run rent-capacity.js 40 2048 false 10000
        More conservative. Useful while many targets are still being prepared.

    run rent-capacity.js 80 512 false 10000
        More aggressive. Useful when hacking is already stable and there is genuine spare RAM.

The remote share worker is:

    rent-share.js

Do not normally run rent-share.js manually. rent-capacity.js sizes and launches it.


1.9 Cleanup
-----------

Cleanup modes:

    run clean.js
    run clean.js strays
    run clean.js workers
    run clean.js share
    run clean.js rent
    run clean.js managed
    run clean.js all

Meaning:

    strays   kills stray deployment scripts only.
    workers  kills weaken.js/grow.js/hack.js workers.
    share    kills rent-capacity.js and rent-share.js, including home rent-capacity.js.
    rent     alias for share.
    managed  kills managed framework scripts across remote hosts, leaving home-level managers alone.
    all      kills the broader framework, including home-level components.

Normal startup uses:

    run clean.js managed
    run clean.js share


1.10 Diagnostics and report scripts
-----------------------------------

Manager console child reports:

    run info-runtime.js
    run info-money.js
    run info-security.js
    run info-payouts.js
    run info-share.js
    run info-diagnostic.js
    run info-startup-config.js

Most support a silent mode used by manager-console.js:

    run info-runtime.js silent <stamp>
    run info-money.js silent <stamp>
    run info-security.js silent <stamp> <securityBuffer>
    run info-payouts.js silent <stamp> <securityBuffer> <moneyTargetRatio> <hackTargetRatio>
    run info-share.js silent <stamp> <reserveGb> <includeHome>
    run info-diagnostic.js silent

Report location:

    /data/manager/*.json

These reports are generated runtime state. They should not normally be committed to Git.


1.11 Log view
-------------

Inspect running script logs on one server:

    run logview.js serverName

Argument form:

    run logview.js [server] [refreshMs] [maxLinesPerScript]

Examples:

    run logview.js joesguns
    run logview.js pserv-0 3000 80

Use this when manager-console.js identifies a specific server worth inspecting.


1.12 Session gains
------------------

Monitor money/experience/share gain since baseline:

    run session-gains.js
    run session-gains.js reset
    run session-gains.js watch 10000

Use this as a separate performance monitor. It is not part of the core control loop.


1.13 File discovery and catalogue
---------------------------------

Discovery script:

    iteration.js

Normal parent:

    upload.js
    infect-start.js

It scans files on remote hosts, copies useful readable files home, and writes catalogues under `/found/` and `catalog/`. These are runtime/generated artefacts, not source files.


1.14 Contract triage
--------------------

Contract report scripts:

    run info-contracts.js
    run info-contract-triage.js

These scan for `.cct` coding contracts and write/report triage data. They are currently diagnostic rather than a full auto-solver framework.


1.15 Optional staged infection scripts
--------------------------------------

Staged/worm subsystem:

    infect.js
    infect-root.js
    infect-deploy.js
    infect-start.js

Normal v2.3 deployment is centralised through upload.js. The staged infection scripts are retained for propagation support and experimentation.


1.16 Experimental scripts
-------------------------

Experimental / non-core:

    faction-control.js
    start-processes.js

`faction-control.js` explores faction work and share/rent interaction. It may require Singularity API access depending on use.

`start-processes.js` is an older diagnostic launcher for process.js. Normal operations should use startup.js, upload.js, assign-targets.js, and manager-console.js instead.

SECTION 2 - SCRIPT INTERACTION AND DEPENDENCE
===============================================================================

2.1 High-level architecture
---------------------------

The suite is layered:

    startup.js
        -> clean.js
        -> buy-servers.js              optional
        -> upload.js
        -> assign-targets.js
        -> rent-capacity.js
        -> check-infection.js
              -> manager-console.js
                    -> info-runtime.js
                    -> info-money.js
                    -> info-security.js
                    -> info-payouts.js
                    -> info-share.js

Runtime target management:

    process.js
        -> weaken.js
        -> grow.js
        -> hack.js

Share/rent spare RAM management:

    rent-capacity.js
        -> rent-share.js
        -> /data/manager/share-control.json

File discovery:

    upload.js or infect-start.js
        -> iteration.js
            -> /found/<server>_files.json
            -> catalog/json/*.json

Contracts:

    info-contracts.js
    info-contract-triage.js
        -> discover .cct files and classify them


2.2 Why startup.js owns orchestration
------------------------------------

startup.js exists to make the recovery path deterministic.

Without it, the operator has to remember this sequence:

    clean managed scripts
    clean share scripts
    maybe buy servers
    upload scripts
    assign targets
    restart rent/share manager
    open dashboard

The script order matters:

1. Cleanup must happen before deployment to avoid stale workers and stale rent-share processes.
2. Purchases must happen before deployment/assignment so new or upgraded servers are used.
3. Upload must happen before assignment because remote worker hosts need process.js and worker scripts.
4. Assignment must happen before diagnostics if you want the dashboard to reflect actual management state.
5. Rent/share must start after assignment so it only consumes remaining spare RAM.


2.3 Why upload.js is central deployment
---------------------------------------

v2.3 treats upload.js as authoritative.

It recursively scans from home, roots what it can, copies the current source payload, starts process.js locally where possible, and optionally starts staged infection.

Central deployment is easier to reason about than pure worm propagation because:

- home has the master copies;
- deployment is repeatable;
- all reachable rooted hosts are treated consistently;
- stale remote copies can be removed deliberately;
- rent-capacity.js can remain home-only.


2.4 Why assign-targets.js exists
--------------------------------

Some money servers are too small or too busy to host process.js effectively. assign-targets.js lets larger hosts manage those targets remotely:

    process.js runs on pserv-0
    target argument is n00dles
    weaken/grow/hack workers also run from pserv-0 against n00dles

This allows the suite to manage all money targets, including low-RAM ones.


2.5 Why process.js is separate from weaken/grow/hack
---------------------------------------------------

process.js is a persistent low-thread controller. weaken.js/grow.js/hack.js are disposable one-shot workers.

This separation matters because:

- process.js can continually reassess target state;
- workers can use many threads without embedding control logic;
- stale workers can be killed when the required action changes;
- state can be written for diagnostics without bloating worker scripts;
- the same process.js logic works locally or remotely.


2.6 Why manager-console.js uses child report scripts
---------------------------------------------------

manager-console.js does not try to calculate everything itself. It launches focused info scripts and reads their JSON reports.

This avoids a single oversized dashboard script and allows the same data to be used by:

- the console;
- AI handoff diagnostics;
- manual inspection;
- future auto-tuning logic.

The current report files are:

    /data/manager/runtime.json
    /data/manager/money.json
    /data/manager/security.json
    /data/manager/payouts.json
    /data/manager/share.json
    /data/manager/ai-diagnostic.json
    /data/manager/startup-config.json

These are generated as required.


2.7 Why rent-capacity.js starts after assignment
-----------------------------------------------

rent-capacity.js fills spare RAM with share work. If it starts too early or is too aggressive, it can consume RAM that should be used for weaken/grow/hack preparation.

The v2.3 order is therefore:

    assign money workers first
    then start controlled share/rent filler

rent-capacity.js also has a cap and reserve:

    maxSharePct limits the proportion of each host usable for share.
    reserveGb leaves a fixed RAM buffer on each host.

This makes share useful without letting it dominate preparation.


2.8 Compatibility role of check-infection.js
--------------------------------------------

check-infection.js is retained because it is the historic command muscle-memory entry point.

Current behaviour:

    check-infection.js -> manager-console.js

It should stay small. Detailed logic belongs in manager-console.js and the info-* scripts.

===============================================================================
SECTION 3 - PSEUDOCODE AND RATIONALE
===============================================================================

3.1 startup.js
--------------

Pseudocode:

    assert current host is home
    parse startup arguments
    verify required scripts exist

    print plan

    if clean requested:
        run clean.js managed
        wait
        run clean.js share
        wait

    if buyServers requested:
        run buy-servers.js spendRatio
        wait

    run upload.js
    wait

    run assign-targets.js assignMinRam assignPerHost assignAllowMoneyHosts
    wait

    if startRent:
        kill existing rent-capacity.js on home
        run rent-capacity.js maxSharePct reserveGb includeHome loopMs

    if restart-required.txt exists:
        remove it

    run check-infection.js

Rationale:

startup.js is the reliable recovery command. It is deliberately procedural because startup order is part of the system's correctness. The share/rent layer is restarted after assignment so it fills spare capacity rather than competing with newly assigned money workers.


3.2 clean.js
------------

Pseudocode:

    assert current host is home
    mode = requested cleanup mode or strays
    resolve aliases such as rent -> share
    choose scripts for mode

    for every scanned server:
        decide whether home should be included
        for each selected script:
            kill all matching processes

    print table of killed scripts

Rationale:

Cleanup must be selective. Killing every script every time is simple but disruptive. v2.3 distinguishes managed money scripts from share/rent scripts because rent-capacity.js runs on home while most money workers run remotely.


3.3 upload.js
-------------

Pseudocode:

    assert current host is home
    verify payload files exist
    scan all servers from home, excluding home

    for each server:
        attempt root using available port openers
        if no root:
            skip

        stop managed runtime scripts on server
        remove old managed files, including stale remote rent-capacity.js
        copy fresh payload scripts

        if server has max money:
            start process.js with target = server

        start iteration.js if possible

        if worm mode requested:
            start infect.js

    print deployment summary

Rationale:

upload.js is the authoritative deployment route. It ensures remote hosts have current code and clears old remote copies. It deliberately keeps rent-capacity.js home-only while deploying rent-share.js where it may be needed.


3.4 assign-targets.js
---------------------

Pseudocode:

    assert current host is home
    scan network

    kill old remote process/worker assignments

    identify money targets that need remote management
    identify eligible worker hosts
        rooted
        enough RAM
        preferred: purchased/cloud servers, MooMF hosts, non-money servers
        optional: money servers if allowed

    copy process.js and workers to worker hosts

    for each target:
        choose a host with assignment capacity
        start process.js on that host with target as argument

    print summary

Rationale:

This separates target value from host RAM. A small server can be profitable but unable to host its own controller. Remote assignment lets the suite manage the whole money network, not only servers large enough to run locally.


3.5 process.js
--------------

Pseudocode:

    host = current host
    target = arg0 or host
    parse securityBuffer, moneyTargetRatio, hackTargetRatio, sleepMs
    verify target exists and is not home
    verify worker scripts exist on host

    loop forever:
        read target root, money, security

        if no root:
            desired action = idle
            reason = noRoot

        else if target has no money:
            desired action = idle
            reason = noMoney

        else if current security > min security + buffer:
            desired action = weaken
            wanted threads = security excess / weaken effect
            reason = security

        else if current money < max money * moneyTargetRatio:
            desired action = grow
            wanted threads = growth analysis to threshold
            reason = money

        else:
            desired action = hack
            wanted threads = hackTargetRatio / hackAnalyze(target)
            reason = payout

        kill stale workers for this target on this host
        if desired action needs a worker:
            calculate runnable threads from free RAM
            launch weaken/grow/hack worker

        write process-state JSON
        sleep

Rationale:

The controller encodes the basic Bitburner money loop: security first, money second, payout last. Security is prioritised because high security slows future operations and reduces hack value. Money is refilled before hacking so the eventual hack has a useful base. Hacking is deliberately delayed until both conditions are acceptable.


3.6 weaken.js / grow.js / hack.js
---------------------------------

Pseudocode:

    target = arg0 or current host
    reject invalid targets
    perform exactly one operation:
        weaken(target)
        grow(target)
        hack(target)
    exit

Rationale:

Workers are intentionally dumb. This makes RAM cost predictable and keeps the decision logic in process.js. It also makes it easy to run many threads of a worker without multiplying control logic.


3.7 rent-capacity.js
--------------------

Pseudocode:

    parse maxSharePct, reserveGb, includeHome, loopMs
    verify rent-share.js exists on home

    loop forever:
        scan all rooted hosts with RAM
        filter to share candidates

        for each host:
            copy rent-share.js if missing
            calculate current share threads
            calculate non-share RAM usage
            share budget = maxRam * maxSharePct - nonShareUsedRam - reserveGb
            desired threads = floor(share budget / rent-share RAM)

            if current share threads differ significantly from desired:
                kill current rent-share.js
                restart with desired threads
            else leave unchanged

        print share report
        write /data/manager/share-control.json
        sleep loopMs

Rationale:

This script turns otherwise idle RAM into useful share power, but with two restraints: a percentage cap and a fixed reserve. The goal is filler utilisation, not domination. If grow/weaken/hack work expands, non-share RAM increases and rent-capacity.js naturally reduces share threads on the next loop.


3.8 rent-share.js
-----------------

Pseudocode:

    loop forever:
        await ns.share()

Rationale:

This is the share equivalent of weaken/grow/hack workers: very small, very specific, and controlled by a separate manager.


3.9 manager-console.js
----------------------

Pseudocode:

    open console tail
    mode = arg0 or overview

    verify child info scripts exist
    run child scripts in silent mode
    wait for reports or timeout

    read report JSON files

    if mode is money:
        print money table
    else if mode is security:
        print security table
    else if mode is payouts:
        print payout readiness table
    else if mode is runtime:
        print root/deployment/process table
    else if mode is share:
        print share/rental table
    else if mode is actions:
        print suggested actions
    else if mode is server:
        print one-server cross-report view
    else:
        print overview and actions

Rationale:

The console is a reader and formatter, not the source of truth. The info scripts produce machine-readable reports. This makes it easier to extend diagnostics without continually expanding one monolithic dashboard.


3.10 info-runtime.js
--------------------

Pseudocode:

    scan network
    map process.js instances by target
    count rooted/unrooted servers
    count money targets and managed targets
    count worker types: weaken/grow/hack
    inspect payload deployment and restart marker
    write /data/manager/runtime.json

Rationale:

Runtime health is about whether the system is deployed and active. It intentionally does not decide target profitability; that belongs in money/security/payout reports.


3.11 info-money.js
------------------

Pseudocode:

    scan money servers
    for each target:
        read current money and max money
        compare to moneyTargetRatio
        record ready/low state
    aggregate totals
    write /data/manager/money.json

Rationale:

Money readiness is separate from security readiness. A target may be safe but empty, which means it needs grow, not hack.


3.12 info-security.js
---------------------

Pseudocode:

    scan money servers
    for each target:
        read current security and minimum security
        allowed = minimum + securityBuffer
        excess = max(0, current - allowed)
        estimate weaken ETA
    sort worst targets
    write /data/manager/security.json

Rationale:

Security excess is one of the best preparation indicators. It explains why hacking may be stalled even when money exists.


3.13 info-payouts.js
--------------------

Pseudocode:

    scan money servers
    for each target:
        read money and security readiness
        compute hackAnalyze(target)
        if hackAnalyze is zero:
            classify as preparedButUnhackable if otherwise ready
        else estimate hack threads and hack money
        classify blockedByMoney, blockedBySecurity, hackReady, etc.
    write /data/manager/payouts.json

Rationale:

This report prevents false optimism. A server with full money and minimum security is not necessarily hack-ready if hackAnalyze returns zero for the current player state.


3.14 info-share.js
------------------

Pseudocode:

    scan share-capable hosts
    find rent-capacity.js manager process
    find rent-share.js worker processes
    total share threads and share RAM
    estimate possible extra share threads
    read share power if available
    write /data/manager/share.json

Rationale:

The share layer can look like generic RAM usage unless separated. A dedicated report shows whether spare capacity is being used productively and whether share might be too aggressive.


3.15 info-diagnostic.js
-----------------------

Pseudocode:

    run/read manager reports
    collect expected files
    collect existing report summaries
    build action suggestions
    include compatibility fallbacks for old/new share field names
    write /data/manager/ai-diagnostic.json

Rationale:

This is the AI handoff/report package. It should describe state, not control the system. Its value is to compress the current suite status into a portable diagnostic JSON.


3.16 buy-servers.js
-------------------

Pseudocode:

    assert home
    parse spend ratio, prefix, dry-run, tail
    calculate budget = home money * spend ratio
    detect purchased/cloud server API shape
    delete stale restart-required marker

    while server count below limit and budget allows:
        buy largest affordable power-of-two server

    if server limit reached:
        repeatedly upgrade smallest useful server if budget allows

    if changes made:
        write restart-required.txt

    print summary

Rationale:

The script first increases count, then capacity. Once the purchased server limit is full, upgrading the smallest servers gives the cleanest path toward a uniformly large fleet.


3.17 logview.js
---------------

Pseudocode:

    server = arg0 or current host
    loop:
        list running processes on server
        for each process:
            print pid, filename, args
            print recent logs
        sleep refreshMs

Rationale:

The manager console shows board-level state. logview.js is for investigating a specific host when something looks stuck or ambiguous.


3.18 iteration.js
-----------------

Pseudocode:

    if current host is home:
        exit

    list files on current server
    ignore framework/runtime files
    for each interesting file:
        if downloadable type:
            copy home
        record catalogue entry

    write /found/<server>_files.json
    copy catalogue home

Rationale:

Discovery is useful, but it should not pollute the catalogue with the automation framework itself. v2.3 ignores rent/share scripts and runtime report paths.


3.19 contract reports
---------------------

Pseudocode:

    scan network or known file lists
    find .cct files
    collect contract type, host, and file name
    classify/triage by solvability or type
    print/write report

Rationale:

Coding contracts are valuable but diverse. v2.3 has discovery/triage rather than full solving, keeping this separate from the money automation loop.


3.20 staged infection scripts
-----------------------------

Pseudocode:

    infect.js:
        copy stage scripts
        scan neighbours
        root/deploy/start each neighbour

    infect-root.js:
        use available port openers
        nuke target if possible

    infect-deploy.js:
        copy payload to target

    infect-start.js:
        start infect.js, iteration.js, and process.js on target where appropriate

Rationale:

These scripts preserve worm-style deployment as a secondary option. Central upload remains easier to audit and is the normal v2.3 path.


===============================================================================
SECTION 4 - WHAT A GOOD SYSTEM LOOKS LIKE
===============================================================================

4.1 Basic command sequence
--------------------------

After augmentation, reload, or a manual reset:

    run startup.js true false

Then monitor:

    run manager-console.js

or:

    run check-infection.js


4.2 Good overview state
-----------------------

In manager-console overview, a good mature state trends toward:

    Network:       rooted servers == total servers
    Managed:       managed money targets == money targets
    RAM used:      high, but not all consumed by share
    Money:         current/max high and rising
    Security:      most targets ready or excess falling
    Payouts:       hack-ready targets eventually greater than zero
    Processes:     weaken/grow early; hack appears later
    Share:         manager running, but capped and leaving reserve

A newly restarted system will often show:

    many weaken workers
    many grow workers
    zero hack workers
    many low-money targets
    some security excess

That is normal during preparation.


4.3 Runtime diagnostics
-----------------------

Command:

    run manager-console.js runtime

Healthy signs:

    totalServers discovered as expected
    rootedServers == totalServers, once port tools are sufficient
    payloadMissing == 0
    managedTargets == moneyServers
    restartRequired == false
    weaken/grow/hack workers make sense for the current preparation state

Warning signs:

    unmanagedTargets > 0
        Run assign-targets.js or startup.js.

    payloadMissing > 0
        Run upload.js or startup.js.

    restartRequired == true
        Run startup.js true false.

    many idle managers while targets are not ready
        Check RAM availability and process logs.


4.4 Money diagnostics
---------------------

Command:

    run manager-console.js money

Healthy signs:

    moneyPct trends upward after startup
    readyTargets increases over time
    lowMoneyTargets decreases over time
    large targets gradually reach the money threshold

Normal early state:

    Many low-money targets after hacking or restart.
    Grow workers should dominate until thresholds are reached.

Warning signs:

    moneyPct stays flat for a long time
        Grow workers may not be running or may be starved of RAM.

    readyTargets high but hack-ready still zero
        Check payouts view; the issue may be hackAnalyze/current player skill.


4.5 Security diagnostics
------------------------

Command:

    run manager-console.js security

Healthy signs:

    notReadyTargets falls over time
    totalSecurityExcess falls over time
    worstExcess falls over time
    ETA values are reasonable

Normal early state:

    Security can take time to recover, especially after large grow/hack activity.

Warning signs:

    security excess not falling
        Weaken workers may be starved or not launched.

    one server remains worst for a long time
        Inspect it:

            run manager-console.js server <server>
            run logview.js <managerHost>


4.6 Payout diagnostics
----------------------

Command:

    run manager-console.js payouts

Healthy signs:

    blockedBySecurityTargets trends down
    blockedByMoneyTargets trends down
    hackReadyTargets eventually rises
    bestTarget appears
    nextHackMoney becomes positive

Important interpretation:

    preparedButUnhackable is not necessarily a script failure.
    It means a target may have money and security ready, but hackAnalyze(target) is zero.
    This often means player hacking level or formulas context is not yet sufficient.

Good mature state:

    Several hack-ready targets.
    Best payout target populated.
    Hack workers visible in runtime view.


4.7 Share diagnostics
---------------------

Command:

    run manager-console.js share

Healthy signs:

    manager running
    shareWorkers > 0 when spare RAM exists
    shareThreads > 0 when spare RAM exists
    share RAM below configured cap
    possibleExtraThreads low when the fleet is saturated by useful work

Warning signs:

    share manager stopped and possibleExtraThreads high
        Run startup.js true false.

    share consumes too much while money/security are blocked
        Restart with a lower rentMaxSharePct or higher rentReserveGb.

Example conservative startup:

    run startup.js true false 0.5 1 2 true true 40 2048 false 10000

Example aggressive startup:

    run startup.js true false 0.5 1 2 true true 80 512 false 10000


4.8 Actions diagnostics
-----------------------

Command:

    run manager-console.js actions

Healthy signs:

    Suggested actions are minor or empty.
    No restart marker.
    No missing scripts.
    No unmanaged money targets.

Use actions as prompts, not as unquestioned authority. The console is a guide; if it points at a server, inspect that server directly.


4.9 Server-specific drilldown
-----------------------------

Command:

    run manager-console.js server <server>

Use this when:

    a target is repeatedly blocked;
    a target is listed as prepared but unhackable;
    a manager appears idle;
    money/security reports disagree with your expectation.

Follow-up:

    run logview.js <host>

where <host> is the local or remote manager host shown in the reports.


4.10 Expected lifecycle after startup
-------------------------------------

Phase 1: Deployment

    upload.js copies scripts
    process.js instances start where possible
    assign-targets.js remote-manages low-RAM targets
    dashboard opens

Phase 2: Preparation

    weaken and grow dominate
    security excess falls
    money percentages rise
    hack-ready may remain zero

Phase 3: Payout

    targets pass security and money thresholds
    payouts report identifies hack-ready targets
    hack workers appear
    money dips and grow/weaken repairs begin again

Phase 4: Spare capacity

    rent-capacity.js fills spare RAM with rent-share.js
    share power rises
    share automatically resizes when non-share work needs RAM

Recommended approach:

    Add an explicit confidence field before attempting answers.


5.3 Better target selection and batching
----------------------------------------

Current process.js uses a simple per-target weaken/grow/hack loop. It is reliable but not optimal.

Next work:

    formulas-based target scoring;
    prioritise best targets rather than managing every target equally;
    introduce batch scheduling: hack/grow/weaken/weaken timing;
    reserve RAM for batch windows;
    use central scheduler rather than independent target controllers.

Potential scripts:

    scheduler.js
    batch-plan.js
    batch-worker.js

Rationale:

The current model is robust and easy to inspect. A batch scheduler would be more profitable but more complex and more sensitive to timing.


5.4 Diagnostic-driven startup tuning
------------------------------------

The project direction is to let info reports guide startup decisions.

Next work:

    use info-startup-config.js recommendations directly;
    choose rentMaxSharePct based on blocked money/security state;
    choose assignPerHost based on purchased server capacity;
    decide whether to buy servers based on current cash and RAM pressure;
    write startup decisions to a report.

Potential improvement:

    startup.js reads /data/manager/startup-config.json
    then chooses defaults dynamically.


5.5 Share/rent policy improvements
----------------------------------

Current rent-capacity.js uses host-local caps and reserves.

Next work:

    global fleet cap as well as per-host cap;
    prep-aware throttling using payouts/security/money reports;
    automatic conservative mode when hackReadyTargets == 0;
    automatic aggressive mode when all targets are prepared;

Example rule:

    if hackReadyTargets == 0 and blocked targets > 0:

5.11 Repo hygiene and runtime artefacts
---------------------------------------

Recommended source-control policy:

    commit scripts and documentation;
    ignore runtime/generated JSON and marker files;
    keep generated diagnostics out of Git;
    regenerate reports inside Bitburner as needed.

Useful .gitignore patterns:

    data/**/*.json
    catalog/**/*.json
    found/**/*.json
    *_cat.json
    servers.json
    *infect-version*.txt
    restart-required.txt
    process-state.json
    session-gains-*.json

Rationale:

Runtime files describe one game state. They are useful for diagnostics, but they are not source code.
